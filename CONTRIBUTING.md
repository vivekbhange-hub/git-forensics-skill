# Contributing

Thanks for helping. This pack is small on purpose, so a few rules keep it that way.

## Ground rules

- Helper scripts use the Python standard library and the `git` command line only, run on Python
  3.9+, make no network calls, only run read-only git commands (`log`, `blame`, `ls-files`,
  `rev-parse`), stream their input and produce the same bytes for the same history. No `match`
  statements, no `X | Y` type unions at runtime, no `zip(strict=)`.
- Every script change comes with a test in `tests/`. Run the suite from the repo root:

  ```
  python -m unittest discover -s tests -v
  ```

  Tests that build a repository need `git`; without it they skip with a message.
- If your change alters what the demo produces, regenerate the committed outputs and include them
  in the same pull request:

  ```
  python examples/regenerate.py
  python examples/regenerate.py --check
  ```

- Write files with LF line endings (`.gitattributes` enforces this in git). In scripts, write
  with `write_bytes` or `open(..., "w", newline="\n")`.
- Skills keep the frontmatter format checked by `tests/test_repo.py`: `name` equals the folder
  name, the description says what it does and lists trigger phrases, and the body has "Inputs",
  "Outputs", "Steps", "Decision rules" and "What NOT to do" sections.
- Numbers quoted in the README as tool output must be copied from `examples/output/`. The test
  suite checks every line of a README block fenced as `output` against those files.
- Plain, specific writing. No marketing language.

## The shared git core

`hotspots.py`, `coupling.py` and `owners.py` each carry a copy of the same block between the
lines `# ---- begin shared core` and `# ---- end shared core ----`: running git, streaming and
parsing `git log -z --numstat`, rename following, exclude globs and file helpers. Skill folders
must stay self-contained, so the block is duplicated rather than imported.

When you change it, edit one copy, paste the same text into the other two and run the tests.
`tests/test_repo.py` fails if the three copies differ.

## Fixtures and the synthetic history

The demo history is generated by `examples/regenerate.py` with fixed author names, emails and
commit dates. Keep it fictional: `example.com`, `example.net` or `example.org` addresses and
invented names. Never commit a real repository, a real history or a `.git` folder: the demo is
built in a temporary folder or in `examples/demo-repo/`, which is git-ignored. A nested repository
inside this one would be committed as a submodule.

Tests build small repositories through `tests/_gitrepo.py` with fixed dates, so results do not
depend on the day they run or on your global git configuration (`GIT_CONFIG_GLOBAL` is pointed
at an empty file).

## Parsing and scoring rules

Changes to what counts as churn, a fix subject, a bulk commit, a test pair or a bot need a test
for the case that motivated them and a test for a nearby case that must not change. Per-author
data belongs in the ownership report only; hotspots and coupling stay at file level.

## Conduct

Be kind and specific. This project follows the spirit of the
[Contributor Covenant](https://www.contributor-covenant.org/version/2/1/code_of_conduct/).

## Releasing

Bump `version` in `.claude-plugin/plugin.json` and add a matching `## [x.y.z] - YYYY-MM-DD`
section to `CHANGELOG.md`; the test suite checks that they agree.
